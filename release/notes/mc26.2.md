# OptiFabric Reforged 2.2.6+mc26.2

**Minecraft 26.2** / Fabric Loader 0.19.5 / **Java 25** / 需求 OptiFine `preview_OptiFine_26.2_HD_U_K2_pre1.jar`

## 2.2.6 改了什么(本版):把 1.21.x 线重写过的 `LocalSlotLayoutFix` 移植过来

**本版修的是一处类库级缺陷**:`distanthorizons`(Distant Horizons)在 **26.2** 上**启动阶段就崩,连主界面都到不了**。
只有 OptiFine 在场时才会坏,报错落在 DH 自己那个 `@Inject` 上:

```
[main/ERROR]: Critical injection failure: LVT in net/minecraft/client/renderer/GameRenderer::renderLevel(
Lnet/minecraft/client/DeltaTracker;)V has incompatible changes at opcode 286 in callback
DistantHorizons.fabric.mixins.json:client.MixinGameRenderer from mod distanthorizons->@Inject::renderLevel(…)
Caused by: java.lang.RuntimeException: Mixin transformation of net.minecraft.client.renderer.GameRenderer failed
```

**根因**:OptiFine 会**重编译它补丁的那些方法**,它的 javac 把**它自己新增的局部变量**放在源码里出现的位置,于是
**游戏自己的局部变量被整体往上挤**。Mixin 读局部变量表有两种方式,这一处两种都会坏:

1. **按槽位顺序** —— `CallbackInjector` 用 `getFirstNonArgLocalIndex(args)` 往上取前若干个非空局部变量来建回调的
   描述符,顺序对不上就报上面那条 `LVT … has incompatible changes at opcode N`(DH 撞的是这一种);
2. **按绝对槽位** —— MixinExtras 的 `@Local(index = N)` 糖取 `locals[N]`,那个槽位上是别的类型时糖根本建不起来
   (`SugarApplicationException: Unable to find matching local!`)。

**修复**:把 1.21.x 线重写过的 `LocalSlotLayoutFix` **逐字节**移植过来(37,453 字节,SHA-256
`85EF437444F637EC15DC63CA810A9348998FEBE751F1F9F4509113E12E103BB1`,取自侧分支 `tf-localscope` 的 `1bf3e4b`),
按这一线的**官方名**注册两条(`desc` 留空,按 OptiFine 那份类自带的描述符办事):

```java
registerFix("net/minecraft/client/renderer/GameRenderer",
        new LocalSlotLayoutFix(null, "render", "renderLevel"));
registerFix("net/minecraft/client/renderer/LevelRenderer",
        new LocalSlotLayoutFix(null, "renderLevel"));
```

它**按作用域**把两张局部变量表配对(可比的是「按槽位顺序排列的描述符序列」,用最长公共子序列对齐),把**游戏自己的**
槽位放回游戏声明的编号,OptiFine 自己的槽位搬到局部区间末尾;一个槽整体搬、绝不拆开,同时活着的两个槽不合并,帧由管线
本来就在用的 `FrameComputingWriter` 重算。**它不删 OptiFine 的任何代码、不加任何指令。**

因此 **`@Local(index = N)` 那一类失败整类消失** —— 不再取决于某个 sugar 恰好落在第几个槽位。这一线上原本**没有**任何
其它管局部变量布局的代码,不会重复施加。

**本版实测**(干净临时 worktree、自己的实例副本、**每次运行前清空 `.optifine` 缓存**、Java 25、各自的 OptiFine 预览版):

|---|---|---|
| DH 复现:出厂 **2.2.3** | 4 jars → `Loading 51 mods` | **FAIL,13 秒**,就是上面那条 `opcode 286` |
| DH 对照:出厂 **2.2.4** | 同上 | **FAIL,21 秒**,同一行 |

前者是 OptiFabric 自己的类接管/元数据状态那一路,后者失败在 OptiFine **自己重编译出来的方法体**里,两者都不是槽位问题
(实测见 `threefix\REPORT.md`)。26.2 上光影照旧不可用(OptiFine 这个构建自己取消了光影包加载)。

## 2.2.4 改了什么(上一版):把 Mixin 类元数据的 cache drop 收窄到顶层类

2.2.1 引进、2.2.3 只是绕过去的那个 Mixin 类元数据 cache drop,现在**只删顶层类**的条目:嵌套类(`GuiRenderer$Draw`
这类)保留自己的缓存。循环里加的就是一条判断:

```java
if (internalName.indexOf('$') >= 0) continue;   // nested classes keep their cached metadata
```

**为什么**:`Injector.checkCoerce` → `canCoerce` → `ClassInfo.forType` 读的正是这个 drop 删掉的 `ClassInfo` cache,
而 `GuiRenderer$Draw` 就是被本模组接管过去的类之一 —— 删掉嵌套条目等于把 accessor mixin 加上去的那条接口一起删了,
Fabric API 的 `@WrapOperation` 于是整个类变换失败(就是 2.2.3 那条 `Cannot @Coerce`)。而 2.2.1 当初要修的
**1.21.x `LVTGeneratorError`** 是**顶层类一个方法的 access 标志**(`class_757` / `GameRenderer.getFov` 从 private 放宽成
public),嵌套条目根本不描述它 —— 所以收窄以后那一处保护**仍然在**。2.2.3 的 `AddInterfaceFix` **保留**:
`drop on + iface off` 两边都 FAIL,它是让 jar 能起来的那一半。

**本版实测**(干净临时 worktree、Loader `0.19.5`、Java 25、各自的 OptiFine 预览版):

| 手臂 | 模组 | 结果 |
|---|---|---|
| 本版,26.2 | 17 jars → `Loading 118 mods`(C2ME 等,见 CHANGELOG) | **PASS,到主界面并进世界**(12 s / 16 s);`Cannot @Coerce`、`InvalidInjectionException`、`Mixin apply … failed`、`LVTGeneratorError` **各 0** |
| 本版,26.1.2 | 19 jars → `Loading 118 mods` | **PASS,到主界面并进世界**(12 s / 16 s);同上四项各 0 |
| 出厂 2.2.3(未收窄)对照,26.1.2 | 同一套 20 jars | **PASS,主界面** —— 这套模组集里没有任何东西依赖未收窄的 drop |

**边界**:两个 PASS 都在 28 秒内结束、只进了一个世界、**没有光影包**、没有压测;`modernfix`/`noisium` 的 1.21.1
构建在 26.x 上直接拒载(`classTweaker` 命名空间)所以不在集合里;`immediatelyfast` 在两个 26.x 版本上都因
`MixinRenderTypes` 找不到注入目标而失败(**在出厂 2.2.3 上同样失败**,与这次改动无关,未查清归属)。

下面的正文仍是 2.2.3 的说明,对 2.2.4 逐条继续适用,除了上面这一处。

状态:**2.2.2 及更早的 26.x 版本起不来**(Fabric API + 本模组 + OptiFine 这一最常见组合),本版(2.2.3)修的就是它 —— 下面是症状、根因、修复与实测对照;2.2.1 的那处修复在 **1.21.x 线上已真机实测**(主界面、进世界、光影包在世界里编译),2.2.2 没有改代码(只改 `fabric.mod.json` 的声明与文档)。

> ### ⚠️ 2.2.2 及更早的 26.x 版本**根本起不来** —— 本版(2.2.3)就是修这一处,请务必更换
>
> **症状**:在**最普通**的配置下 —— Fabric API(**26.2 用 `0.160.0+26.2`**,26.1.2 用 `0.155.3+26.1.2`)+
> 本模组 + 对应版本的 OptiFine,**没有别的模组** —— 客户端在启动阶段直接崩掉,连主界面都到不了。日志里是
> Fabric API **自己那个 mixin** 失败,不是本模组的名字:
>
> ```
> Mixin apply for mod fabric-rendering-v1 failed fabric-rendering-v1.mixins.json:GuiRendererMixin from mod
> fabric-rendering-v1 -> net.minecraft.client.gui.render.GuiRenderer:
> org.spongepowered.asm.mixin.injection.throwables.InvalidInjectionException @WrapOperation operation wrapper
> method net/minecraft/client/gui/render/GuiRenderer::fixNonQuadIndexing from
> fabric-rendering-v1.mixins.json:GuiRendererMixin from mod fabric-rendering-v1 has an invalid signature.
> Cannot @Coerce argument type net.minecraft.client.gui.render.GuiRenderer$Draw at index 4 to
> net.fabricmc.fabric.mixin.client.rendering.GuiRendererDrawAccessor
> ```
>
> 26.1.2 上是同一处、同样的报错,只是那个接口在那一版叫 `.../DrawAccessor`(处理器签名里用的是
> `VertexFormat$IndexType`,因为那一版的 `RenderPass.setIndexBuffer` 收的是它)。
>
> **责任在哪一方,四条对照已经把它钉死**(每条只差一个变量):
>
> | 配置 | 结果 |
> |---|---|
> | 只有 Fabric API | **正常** |
> | Fabric API + 本模组,**不放 OptiFine** | **正常** |
> | Fabric API + 本模组 + OptiFine(不放别的模组) | **失败**,就是上面那句 |
> | 再加任何别的模组(Fabric API + 本模组 + OptiFine + 其它) | 同样**失败** |
>
> 也就是说:**只有 OptiFine 在场时才会坏**,而报错落在 Fabric API 的注入器上。根因不在 Fabric API,也不在
> "哪个方法被改名了"。
>
> **根因**:OptiFine 重编译过的类是由本模组交给加载器的,Mixin 从这份字节建元数据时,**Fabric API 那个
> accessor mixin 加的接口还没在类上**。而 Fabric 的 `@WrapOperation` 处理器要把正在画的
> `GuiRenderer$Draw` 当成 `GuiRendererDrawAccessor` 用,Mixin 用 `ClassInfo#canCoerce` 校验这一步 ——
> 问的是"**这个接口现在是 `GuiRenderer$Draw` 的超类型吗**" —— 答案是否。于是整个 `GuiRenderer` 这个类
> 变换失败,启动到此为止。请注意这不是方法体问题:`GuiRenderer.executeDraw(Draw, RenderPass)` 的描述符
> 与局部变量槽位两边**完全一样**,`GuiRenderer$Draw` 的成员(以及 `executeDrawRange` 的指令表)也与原版
> **逐字节相同**;缺的只是一条**类级别的接口**。
>
> **修复**(本版,2.2.3):新增 `patcher/fixes/AddInterfaceFix.java` —— 一个 `ClassFixer`,在
> `OptifineFixer.registerOfficialNameFixes()` 里对 `net/minecraft/client/gui/render/GuiRenderer$Draw`
> 注册一次。它把接口**从类路径上找出来**:遍历已加载模组的 mixin 包(包名读自各自的 `*.mixins.json`,
> 包括 jar 里 `META-INF/jars/` 下的嵌套 jar),找 `@Mixin(targets=…)` 指向这个类的**接口**,并且只接受
> **声明了目标类当前没有的方法**的候选 —— 然后把这个接口加到 OptiFine 那份 `Draw` 上。accessor 方法本身
> **不写**:那些由 Mixin 从同一个 mixin 生成(自己写进去会让整个类因
> "`cannot overwrite method … because @Overwrite is required by the parent configuration`" 失败,已实测)。
> 日志里会打出:
>
> ```
> [OptiFabric] Added net/fabricmc/fabric/mixin/client/rendering/GuiRendererDrawAccessor to
> net/minecraft/client/gui/render/GuiRenderer$Draw so the mixin that coerces to it can apply
> (its fabric$pipeline()Lcom/mojang/blaze3d/pipeline/RenderPipeline;,
> fabric$Draw()Lnet/minecraft/client/renderer/StagedVertexBuffer$Draw; will be contributed by Mixin)
> ```
>
> **为什么接口是按类路径查、而不是写死名字**:它在两个版本里**名字不同**(26.2 是
> `GuiRendererDrawAccessor`,26.1.2 是 `DrawAccessor`)。写死一个名字会让另一条线在 fixer 内部抛
> `ClassNotFoundException` —— **已实测**,所以本版不这么做。
>
> **实测对照(A/B)**:
>
> | 手臂 | 结果 |
> |---|---|
> | 旧 jar(2.2.2),26.2,Fabric API + 本模组 + OptiFine | **失败,23 秒** |
> | 旧 jar(2.2.2),26.1.2,同上 | **失败,21 秒** |
> | **新 jar(2.2.3),26.2** | **主界面,20 秒**,`Loading 49 mods` |
> | **新 jar(2.2.3),26.1.2** | **主界面,20 秒**,`Loading 49 mods` |
> | **新 jar(2.2.3),26.2 + C2ME** | **主界面,17 秒**,`Loading 79 mods` |
> | **新 jar(2.2.3),26.2 + C2ME,进世界** | **世界加载并渲染**:`Starting integrated minecraft server version 26.2`、`Loaded 1585 recipes`、`Time elapsed: 1424 ms`;`Cannot @Coerce` / `InvalidInjectionException` / `Mixin apply … failed` **各 0 条** |
>
> **诚实的边界**:上面那次"进世界"只跑了约 **40 秒**(不是压测,也不是长时间挂机);**26.1.2 只到主界面,
> 没有进世界**;这个修复只在两个 26.x 版本 + 各自参考安装里那份 Fabric API 上验证过(写的时候是按类路径找
> 的,理论上能跟着改名走,但只实测了 `0.160.0+26.2` 与 `0.155.3+26.1.2`);另外**没有查明**为什么 Mixin 的
> accessor 那一趟本来没有走到本模组提供的这份 `Draw` 上 —— 报错的方向、`@Coerce` 的判定与"补上接口就好"
> 这三件事都是实测结论,唯独最初那条 accessor mixin 为什么漏掉,没有定论。
>
> ### 2.2.2 改了什么(上一版):`sodium` 同时声明进 `conflicts` 与 `breaks`
>
> `fabric.mod.json` 里 `sodium` 现在同时写在 `conflicts` 与 `breaks` 两处(`*`;**原有的 `conflicts` 条目保留**),
> 两份 README 也把这份已声明的不兼容清单写成了文字。**在 Fabric Loader 0.19.5 上,两个字段都不会阻止游戏启动**:
> `mods/` 里同时有 sodium 时,日志开头是 `Warnings were found!` 并点名这条冲突,然后照常进入 `Loading <N> mods:` ——
> **没有** `Incompatible mods found`,也没有 `HARD_DEP` 之类的拒载。所以这是一条**声明,不是闸门**,请读成
> "作者已知这个组合会坏",而不是"装了会被拦住"。(那次实测是在 1.21.x 线上做的;`conflicts` 与 `breaks` 由加载器
> 自身处理,与是哪条线无关。)另外,`sodium` 自己那份元数据只在 `breaks` 里、针对的是旧 id `optifabric`,
> 而本线从 2.0.0 起是 `optifabric_reforged` —— 所以加载器读到的就是本模组这一条。

> 那一版的光影是正常的。
>
> 为什么不去"修"它:2.1.0 试过,结果更糟(见下)。

> ### ⚠️ 装了 2.2.0 及更早版本的人请换成这一版(2.2.1 修的是 mixin 整个类变换失败)
>
> OptiFine 改过的类里,只要有 mixin 需要解析局部变量(`@ModifyVariable`、locals 捕获),Mixin 就会拿**它自己缓存的

> `LVTGeneratorError`,Fabric 那边只看到一句 `Mixin transformation of net.minecraft.class_757 failed`。2.2.1 起
> 本模组在替换掉这些类之后**丢掉 Mixin 为它们缓存的元数据**,Mixin 便按实际拿到的字节重建。**换 jar 即可,不用改配置,
> 也不用改受影响的模组。**细节见下文「2.2.1 改了什么」。

> - **从 2.1.0 升上来的人要撤掉一个改动**:2.1.0 把 OptiFine 那句取消删掉、把光影包加载**强行打开**。结果不是光影变好,

>   删掉即强制重建。

## 这个版本是什么

把 OptiFine 接入 Fabric,用于 **26.2**(2026-09-15 发布)。26.2 与 26.1.2 一样**未混淆** —— 官方名就是运行名,
既没有 yarn,也没有真正可用的 intermediary 可重映射。所以这一版的构建侧一个字都没改:还是 Loom 的非重映射
flavour,目标版本只来自根目录 `gradle.properties` 的 `minecraft_version=26.2`(**没有** `-Pmc`,也没有
`-Pmod_version_base`)。

**2.2.3 改了什么**(本版):**修好"根本起不来"那一处** —— OptiFine 那份 `GuiRenderer$Draw` 上补一条 Fabric API
的 accessor 接口(见文首那一节)。改动只有两处:`patcher/fixes/AddInterfaceFix.java`(新文件,一个 `ClassFixer`,
把接口按类路径找出来再加到类上)与 `OptifineFixer.registerOfficialNameFixes()` 里对
`net/minecraft/client/gui/render/GuiRenderer$Draw` 的**一条注册**。除这一条注册与新 fixer 之外,补丁管线与 2.2.2
逐字节相同,所以 2.2.1 / 2.2.2 的离线数字继续适用(见下文「验证结果」);本版**没有**新增或移除对任何 Minecraft / OptiFine
构建的支持(按 [`docs/VERSIONING.md`](../docs/VERSIONING.md) 的改动表是「修 fixer、修兼容性 → 修订号」)。

**2.2.2 改了什么**(上一版):只有声明与文档 —— `fabric.mod.json` 里 `sodium` 同时写进 `conflicts` 与 `breaks`
(`conflicts` 那条保留),两份 README 补上「声明的不兼容」一节。**代码一个字节没动**,补丁管线、fixer 表与丢
`ClassInfo` 缓存那一步都与 2.2.1 逐字节相同,所以 2.2.1 的离线数字继续适用(见下文「验证结果」)。

**2.2.1 改了什么**(上一版,这里保留它的记录):**丢掉 Mixin 为被本模组替换掉的类缓存的 `ClassInfo`**。

Mixin 会给每个类建一份元数据(`org.spongepowered.asm.mixin.transformer.ClassInfo`)并缓存,内容取自**它的字节码
提供者** —— 在 Fabric 上就是 Knot,也就是本模组的 game transformer。Fabric 在 `preLaunch` 入口点**之前**就已经把
Mixin 的配置准备好(本模组的 `OptifineSetup` 正是在 `preLaunch` 里跑的),所以对本模组替换掉的那些类,缓存里可能
已经存着**游戏自己的**那一份,而 Mixin 稍后拿到、随后要变换的却是 **OptiFine 的**那一份。两者对某个成员的记录一旦
不一致,查找就会落空,而 Locals(局部变量机制,`@ModifyVariable` 与 locals 捕获都走它)没有退路:它用

    ClassInfo#findMethod(name, descriptor, access | INCLUDE_INITIALISERS)

找正在变换的方法,而 `ClassInfo.Member#matchesFlags` 要求**存成 private 的成员必须用 ACC_PRIVATE 查**。OptiFine
重编译 `GameRenderer.getFov`(`method_3196`)时把它从 private 放宽成 public,于是对着缓存里那份**游戏**记录查不到,
Mixin 在 `ModifyVariableInjector.preInject` 里就把**整个类**判失败:

    LVTGeneratorError: Could not locate method metadata for method_3196 generating LVT in net/minecraft/class_757

这一步在 `require` / `expect` **之前**,所以受影响的模组自己无法绕开;Fabric 那边只会把这个异常报成一句
`Mixin transformation of net.minecraft.class_757 failed`。

修复:`GameTransformerHook` 记住**它实际替换掉**的类(Loader 自己打过补丁的类不在此列),安装完这些类之后按**内部名**
(斜杠形式)丢掉它们在 Mixin 缓存里的条目 —— 新文件 `mod/MixinClassMetadata.java`(113 行),每个类最多丢一次,
缓存取不到时只报告一次、不影响其它逻辑(过期元数据仍然能跑,只是那些解析类元数据的 mixin 照旧失败)。Mixin 于是按它
**实际拿到**的字节重建元数据:正在被变换的类通过 `ClassInfo#fromClassNode` 进入 Mixin 的目标上下文,而那只有在缓存里
**没有**条目时才会重建。

**同一个修复在本仓库的 1.21.x 线上先落地**(那条线上一份源码里的同一处改动),并已在 1.21.x 上**真机端到端实测**:
主界面、进世界,以及**光影包在世界里编译**。这一版是把它补到 26.x 的两个产物上;两者源码同源,只有目标 MC 版本不同。

**2.2.0 改了什么**(上一版,这里保留它的记录):新增了 1.21.x 那条线上同一套 **OptiFine 提示 + 官方站下载**功能,按 26.2 的客户端 API 改写
(`GuiGraphicsExtractor`、`EditBox`、`Component`、`setScreenAndShow`、`stop`、`rebuildWidgets`):

- **没有装 OptiFine**:每次启动都在界面上告诉你缺哪个文件(这一次的关闭只在本次会话有效);
- **装的是更旧的预览版**:每个构建只提示一次,记在 `config/optifabric-mismatch-ack.txt`;
- **已装正式版(final)**:完全不提示,哪怕有更新的正式版;
- 提示界面上的 `下载 OptiFine` 按钮**只从 OptiFine 官网取**(`optifine.net/adloadx`,本模组唯一会用的来源),
  下载**保存前先校验**(同时接受 `srg/net/optifine/Config.class` 这种新版布局),旁边就是打开 mods 文件夹;
  地址栏可以换成你自己的地址,那样就只从你填的地方取 —— 本包**不含、也不分发** OptiFine,也不指向任何第三方镜像
  (2.1.1 那一版发布说明里给过的国内镜像地址在这一版删掉了);

  所以 `build.gradle` 多了两条 `compileOnly` 的 JNA 依赖(只编译期使用,不进 jar)。

本版**没有碰光影那条判据** —— 26.2 上光影仍不可用(见文首)。

**版本号为什么是 2.2.1**:按 [语义化版本](https://semver.org/lang/zh-CN/)与
[`docs/VERSIONING.md`](../docs/VERSIONING.md),「修 fixer、修兼容性 → 修订号」。这一版修的是一个会让 mixin 整个类

`2.2.0+mc26.2` 与 `2.2.0+mc26.1.2` 按 §3 冻结(它们那一节记录原样留着)。

`$modVersions`):**这一版两个 MC 版本各出一个 jar**,26.1.2 那一份不再是冻结的 `2.0.0+mc26.1.2`。

**2.1.1 改了什么**(上一版,这里保留它的记录):只有一处 —— `mod/OptifineJarFixer.java` 的 `enableShaderPackLoad`
**只保留 1.21.6 / 1.21.7 那种形状原有的判据**(`ICONST_1, ISTORE, ILOAD, IFNE` 四步**紧邻**),**为 26.2 那种形状写的

结论同时写在类注释与那段行内注释里。1.21.6 / 1.21.7 的修复不变(那是另一种形状,照旧把加载补回来)。

本 jar **只适配 Minecraft 26.2**,不要跨版本使用,也不要拿 1.21.x 的 jar 顶替。

## 26.2 上移动或改名的四处

1. **`Minecraft.setScreen` 没了**:26.2 换成了 `setScreenAndShow`。本模组报告错误时的那次调用因此编译失败
   (`找不到符号: 方法 setScreen(ConfirmScreen)`);26.1.2 上两个名字都在,所以改用 `setScreenAndShow` 之后两边都能编译;
2. **方块描边那一趟搬了家**:26.2 把 `extractBlockOutline` 从 `LevelRenderer` 挪进新类
   `net/minecraft/client/renderer/extract/LevelExtractor`,Fabric API 也跟着搬(它的处理器现在是
   `LevelExtractorMixin.hasMaterialFlagProxy`),于是原来按 `LevelRenderer` 注册的修复不再命中。现在为
   `LevelExtractor` 补了同一对修复(补回被 OptiFine 掏成空壳的原版方法体 + 丢掉原版已不存在的那几个重载),
   **旧判据同时保留** —— 26.1.2 上没有 `LevelExtractor`,那条在新版本上是空操作;
3. **区块重建任务类改名**:`SectionRenderDispatcher$RenderSection$RebuildTask` → **`…$CompileTask`**。OptiFine 把
   `SectionCompiler.compile(...)` 改名后需要把调用者一起改过去,而那条修复按类名注册 —— 不跟着改名,第一次区块重建
   (也就是**开存档后的第一帧**)会抛 `NoSuchMethodError`。现在这条重定向也注册在 `CompileTask` 上(同样与旧的那条并存);
4. **光影包一个都加载不了(OptiFine 26.2 preview 自身的缺陷)—— 这一处故意不修**:这一版的 `Shaders.loadShaderPack`
   把"取消"标志位置真之后就跳过了真正的加载,连 OptiFine 自带的那份光影也不行。**2.1.0 试过强行打开它**:判据确实
   命中了(日志打出 `[Shaders] Loaded shaderpack: ComplementaryReimagined_r5.9.1.zip`),但选了光影包之后世界
   **只画粒子、方块透明**(27 个 program 编译完成,任何日志里都没有报错),同一个实例把 `shaderPack=OFF` 就正常。
   也就是说这一版 OptiFine 的光影管线还没做完,而那句"取消加载"正是让它不插手画面的开关 —— **2.1.1 因此把那条判据
   整段删除,那段字节码原样留给 OptiFine**,26.2 上"光影不可用"作为限制写明(见文首与"已知限制")。

## 已知限制

- **本版(2.2.3)没有查明的一点**:Mixin 的 accessor 那一趟**为什么**本来没有走到本模组提供的这份
  `GuiRenderer$Draw` 上,至今没有定论。已经证实的是失败的那个判据(`canCoerce` 的方向)、补上接口就能修好这两件
  事;最初那条 accessor mixin 为什么漏掉,只是**用接口把它补回来**,不是找到了它漏掉的原因;
- **本版修复的验证范围**:只跑过 26.2 与 26.1.2 两版,以及各自参考安装里那份 Fabric API(`0.160.0+26.2` /
  `0.155.3+26.1.2`)。接口是按类路径找的、不写死名字,理论上能跟着改名走,但没有在别的 Fabric API 构建上实测;
- 26.1.2 的这一份(`2.2.4+mc26.1.2`)**同样带这一处修复**(它上的表现与 26.2 一样是启动即崩,接口名不同);
- **26.2 上光影不可用**:这个 OptiFine 构建里那句取消加载原样留着,在 OptiFine 里选光影包**不会有任何效果、也不会
  报错**;强行打开则会得到"只画粒子、方块透明"的画面(2.1.0 就是这个结果)。光影在 26.1.2 上照旧可用;
- 26.2 的 OptiFine 目前只有 **preview** 构建(`HD_U_K2_pre1`),与 26.1.2 当时一样;
- 多人与抗锯齿没有在 26.2 上重跑,那两项仍是 26.1.2 / 2.0.0 的记录;
- **26.2.1 与 26.3 支持不了**:这两版 Minecraft 确实存在,但 OptiFine 至今没有为它们发布任何构建,没有可移植的对象;
- 26.1.2 这一份在本版里是 `2.2.3+mc26.1.2`,它同样带 2.2.1 的丢缓存修复与 **2.2.3 的这一处接口修复**;
- 依赖 Fabric 渲染器 API(FRAPI)的模组在这一线能拿到**真正的渲染器**,**只有"移动方块提交 / 方块模型提交"这两条
  Fabric 钩子仍被有意停用**(方块破坏裂纹那条没有动,它确实走 Fabric 的渲染器)—— 这条行为自 2.0.0 起没变,
  当时是在 26.1.2 上用 LambdaBetterGrass 实测的;
- 1.21.x 全系列不受影响,仍由那条线自己的 jar 提供(1.21 与 1.21.1 是 `1.1.0`,1.21.3 – 1.21.11 是 `1.1.2`)。
